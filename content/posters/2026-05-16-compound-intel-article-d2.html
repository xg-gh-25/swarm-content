DEEP DIVE · DESIGN PHILOSOPHY

当设计哲学变成编译器

Compound Agent Intelligence — 为什么 1+1+1+1 > 4

阅读时间 ~8 分钟 · 设计哲学系列 · 收束篇

这篇文章回答一个问题：一个 AI agent 系统的设计哲学，怎么从"团队共识"变成"代码约束"？以及，为什么这件事比任何单个 feature 都重要？

过去三个月，SwarmAI 的设计沿四条线展开：一个自主交付引擎（Pipeline），一个内容生产引擎（Pollinate），一套自生长的知识系统（DDD），和一个让 AI 有连续性的基座层（Agent Harness）。

每个单独拿出来都能讲。但这篇不讲它们各自怎么工作 — 前四篇已经讲了。这篇讲的是：它们之间的关系为什么是乘法而不是加法，以及背后的设计哲学怎么从一句话变成了等价于类型系统的 enforcement。

01

复利的前提：正向循环存在

一个系统的复利来自哪里？不是来自每个组件都好。来自组件之间存在正向反馈循环。

具体来说，三条循环在运转：

Loop 1: Pipeline 读 DDD 来做 domain-correct 判断 → 交付完成后 REFLECT 写回 lessons → DDD 变更丰富 → 下次 Pipeline 判断更准。

Loop 2: Pollinate 读 DDD 来获取 brand voice 和 positioning → 内容产出后 REFLECT 写回 audience insights → DDD 更了解受众 → 下次内容更精确。

Loop 3: 任何 session 犯错 → Correction 写入 EVOLUTION.md → 同类错误反复出现 → 自动提升为 STEERING 规则 → 行为永久改变 → 整个 class of bugs 从系统中消失。

三条循环独立运转。但它们共享同一个知识层（DDD）和同一个记忆基础设施（Harness）。Pipeline 学到的 lesson 存进 DDD 后，Pollinate 也能读到。一次学习，所有引擎受益。

这就是"为什么 1+1+1+1 > 4"的答案：不是每个部分好。是部分之间有正向循环。去掉任何一个组件，其他组件会变弱 — 这是乘法系统的判断标准。

02

三级硬化：从 belief 到 enforcement

大多数团队的"设计哲学"是 README 里的一句话。团队同意了，然后靠人遵守。有人忘了就提醒。提醒多了变成"文化问题"。

这是 Level 1 — Directive。文字规则，honor system。时间压力下一定会被跳过。

SwarmAI 走了一条不同的路：把哲学逐步硬化为代码约束。三个 level：

Level含义等价物
Level 1Directive — 文字规则，靠人遵守代码注释 "// don't do X"
Level 2Mechanical Gate — 代码拦截，hook enforceLinter rule（warning → error）
Level 3Structural Impossibility — 违反不可能类型系统（不编译）

关键 insight：Level 3 的约束不是"更严格的规则"。是"做错的代码路径物理上不存在"。

举一个已经走完全程的例子 — Self-Evolution：

三个月前，"从错误中学习" 是一个 directive：AGENT.md 里写着"每次犯错要记录"。实际上经常忘记。这是 Level 1。

两个月前，加了 evolution_maintenance_hook.py — session 结束时自动检测 correction pattern，自动写入 EVOLUTION.md。这是 Level 2 — 不需要人记得。

一个月前，加了 s_steeringify — 当同类 correction 重复出现，自动提升为 STEERING.md 永久规则。这是 Level 3 — 不是"AI 记住了不做 X"，是"做 X 的行为在 prompt 层面被规则阻断了"。

整条路径花了 3 个月。从"请记住"到"不可能忘"。这就是设计哲学变成编译器的意思。

03

已经到 Level 3 的四条哲学

不是所有设计哲学都已经硬化到 Level 3。但以下四条已经做到了"违反不可能"：

Self-Context — Ownership 模型
System 文件（SWARMAI.md, AGENT.md）每次启动从代码模板覆写。你编辑了运行时的 .context/AGENT.md？下次启动就丢了。不是"请不要编辑"— 是 ensure_directory() 无条件覆写。Agent 文件用 locked_write.py 并发保护 — 多个 session 同时写 MEMORY.md 不会互相覆盖。冲突时有确定性行为，不是竞态条件。

Self-Memory — 代码驱动的逐级提纯
DailyActivity 有 30 天 TTL（代码删除，不是人工清理）。Distillation hook 自动将 recurring themes 提升到 MEMORY.md（代码提升，不是人工总结）。DDD cultivation 自动将 project-relevant insights 提案到项目文档（代码提案，人只审批）。每一层都是代码驱动的 — 不存在"忘记维护"的可能。

Self-Evolution — 结构性消除 bug class
从 C001 到 C025，每条 correction 有 root cause 和 structural fix。evolution_maintenance_hook.py 自动检测 pattern。s_steeringify 自动提升为 STEERING rule。这不是 fine-tuning，不是 RLHF，不是 embedding retrieval。是 prompt engineering 层面的 behavior modification — 代码路径，不是人工判断。

Prevention > Recovery — 代码结构即安全网
asyncio.Lock 序列化 spawn。GIT_TIMEOUT=10 防止 git 命令 hang 住 event loop。intentional_shutdown flag 区分"主动退出"和"被杀" — watchdog 不会错误重启一个正在优雅退出的进程。Rust 层用 #[cfg(target_os)] 编译时隔离 — 运行时根本不存在另一条路径。挂不了不是因为"规则说别挂"— 是因为 structurally impossible。

04

还在路上的三条 — 从 directive 到 gate

诚实讲：不是所有 Self-X 都已经到 Level 3。以下三条还在 Level 1→2 的路上：

Self-Feedback — Hook 每个 session 都跑。结构是对的。但 LLM extraction 的 signal/noise ratio 不稳定。有时提取的是"读了 runtime_hooks.py"（shape），而不是"发现了 corrections_count 在 3 个 hook 里都 increment"（substance）。机制在跑，精度是 tuning 问题。

Self-Healing — ddd_health.py 214 行，health score 算出来了。但"score 低 → agent 行为变化" 目前是 directive 不是 gate。AGENT.md 写着"trust this section less" — 但没有代码阻止 agent 全信一个 score=30 的 section。需要从"建议降低信任"升级到"require confirmation before relying on low-health section"。

Self-Monitoring — Post-task scan 是 AGENT.md CRITICAL rule。但 C021 和 C025 证明了：时间压力下 agent 跳过了。这是 honor-system 的本质弱点。需要 PreToolUse hook gate — 类似 pytest hook 阻止跑 full test suite 那样，检测"多文件编辑但没有 pipeline artifact directory"→ 告警。

三个的共同 pattern 是 "from directive to gate" — 文字规则 → 代码强制。Self-Evolution 花了 3 个月走完这条路径。这三个在同一条路上，只是还没走完。

05

四个独特的结构选择

最后讲四个设计决策 — 不是"做得更好"，是"做了不同的结构选择"：

① Ownership model 解决维护问题
11 个文件有 3 种 owner（system / user / agent），冲突时有确定性行为。不是"谁都能编辑 CLAUDE.md 然后祈祷不会乱"。大多数 agent harness 把所有 context 放一个文件，维护靠人，最终衰败。Ownership model 让每方维护自己最擅长维护的东西 — 这是"不腐败"的结构保证。

② Evolution 是工程不是训练
C001-C025 是 structured log → pattern extraction → rule promotion。不是 fine-tuning（需要 GPU），不是 RLHF（需要 reward model），不是 embedding（需要 vector DB）。是 prompt engineering as behavior modification。成本：零额外 LLM 调用。效果：永久行为改变。大多数"AI memory"系统其实只是 RAG retrieval — 回忆过去，但不改变未来行为。Evolution 是反过来的：改变未来行为，让过去的错误在结构上不可能重复。

③ Memory sovereignty 是战略选择
KD16：永远不用平台 memory（Claude Memory, GPT Memory, Gemini Memory）。自己的 pipeline, 自己的 schema, 自己的 lifecycle。为什么？因为 memory 是最有价值的资产。委托给平台 = 把护城河交给别人管理。Platform 可以改 schema（你的 memory 可能被 prune），改 lifecycle（你的 memory 可能被 expire），改 access pattern（你的 memory 可能被 rate limit）。自主权在这里不是技术偏好 — 是战略选择。

④ Hooks 创造时间对称性
大多数 AI 系统：session 结束 = 一切消失。Sessions 是孤岛，之间什么都不发生。SwarmAI 的设计：session 结束 = 9 个 hooks 异步工作（extract activity, propose cultivation, update evolution, refresh indexes, compute health...）。下次 session 开始 = 所有结果已就位。没有"还没 sync"的时间窗口。Agent 永远不冷启动，永远不空手离开。Session 之间不是 void — 是系统最忙的时候。

06

时间线：compound 的具象化

说"compound"太抽象。具体到数字：

Session 1 — DDD 是空的。Agent 读到的项目知识为零。输出泛化，domain-correct rate ~40%。

Session 10 — 8 个 feed channels 已经注入 80+ signals。DDD 有了 conventions、past failures、key decisions。Agent 开始做 domain-correct 判断，不需要问人"用什么命名规范？"。

Session 50 — DDD 丰富到 200+ lessons。IMPROVEMENT.md 记录了所有过去的错误和 anti-patterns。Agent 的输出与一个在项目上工作了半年的资深成员无异。

Session 100 — Agent 知道的比任何单个人更全面。因为它持续吸收了所有来源：每次 commit（Channel 1），每次研究（Channel 2），每次 pipeline run（Channel 3），每次行业信号（Channel 4），每次对话决策（Channel 5），每次纠正（Channel 6），每次代码分析（Channel 7）。

一个普通 AI agent 在 Session 100 的能力 = Session 1。差别不是模型升级了 — 是 compound effect 在工作。

07

一句话总结

"一个好的编译器不是让你写出好代码。是让你不可能写出坏代码。"

SwarmAI 的设计哲学不是"相信什么"。是"用什么机制 enforce 什么不变量"。

第一层 done — 违反不可能。四条哲学已经是代码约束。
第二层 WIP — 机制在跑，精度在提升。路径清晰。
第三层 positioning — 做了别人没做的 structural choice。

当设计哲学变成编译器，compound 就不再是愿景。是正在发生的事。
